# TextSystem - структурований текст на ООП

Навчальний проект за технічним завданням: реструктуризація системи
представлення структурованого тексту (частина 1) плюс спеціальний клас
для керування процесом створення тексту з уніфікованим API (частина 2).

Працюємо тільки з TextSystem. GameSystem до цього завдання не входить.

## Структура проекту

- `TextSystem/ITextElement.cs` - базовий інтерфейс елемента (`Render()`).
- `TextSystem/TextElement.cs` - абстрактний базовий клас усіх елементів.
- `TextSystem/Heading.cs`, `Paragraph.cs`, `Link.cs` - конкретні елементи.
- `TextSystem/TextDocument.cs` - контейнер і рендер документа та змісту.
- `TextSystem/DocumentBuilder.cs` - керування створенням документа (fluent API).
- `Program.cs` - демо того самого сценарію, що й в оригінальному завданні.
- `docs/diagram.puml`, `docs/diagram.png` - діаграма класів.

## Частина 1 - реструктуризація: наслідування, поліморфізм, абстракція

Проблема оригіналу: три класи (`Heading`, `Paragraph`, `Link`) напряму
реалізовували інтерфейс `ITextElement` без спільного базового класу, а
`TextDocument.RenderTableOfContents()` робив `OfType<Heading>()` і ліз у
конкретні поля `Level`/`Text`. Тобто документ знав про конкретний тип,
і додавання нового елемента для змісту вимагало б правити документ.

Рішення:

- **Абстракція** - `TextElement`: абстрактний клас, що реалізує
  `ITextElement` і додає віртуальний метод `GetTableOfContentsEntry()`
  (за замовчуванням повертає null - елемент не входить у зміст).
  Клієнти (`TextDocument`, `DocumentBuilder`) працюють тільки через
  цей абстрактний тип і ніколи не роблять downcast.
- **Наслідування** - `Heading`, `Paragraph`, `Link` успадковують
  `TextElement`. Спільний контракт в одному місці, поведінка за
  замовчуванням теж в одному місці.
- **Поліморфізм** - кожен елемент сам вирішує, як рендеритись
  (`Render()`) і чи давати рядок у зміст (`GetTableOfContentsEntry()`).
  Тільки `Heading` перевизначає другий метод і рахує відступ за своїм
  `Level`. `TextDocument` просто опитує всі елементи в циклі, тому для
  нового типу зі змістом досить перевизначити один метод, а документ
  правити не треба (принцип Open/Closed).

Властивості елементів зроблено незмінними (тільки `get`), рівень
заголовка нормалізується через `Math.Clamp(level, 1, 6)`.

## Частина 2 - клас керування створенням: DocumentBuilder

`DocumentBuilder` - це спеціальний клас-будівельник (з рисами фасада):
він володіє об'єктом `TextDocument` і веде весь процес створення.

- Уніфікований API: `AddHeading()`, `AddParagraph()`, `AddLink()`,
  `MoveElement()`, `Clear()` замість ручної комбінації `new` + `AddElement`.
- Fluent-ланцюжки: кожен метод повертає `this`, сценарій збирається
  одним виразом.
- Делегування читання: `RenderDocument()`, `RenderTableOfContents()`,
  `Count` прокидають виклики у внутрішній документ.
- Фінал: `Build()` повертає готовий `TextDocument`.

Клієнтський код (`Program.cs`) більше не створює елементи напряму.

## Діаграма класів

![Діаграма класів TextSystem](docs/diagram.png)

Джерело: `docs/diagram.puml` (рендер: PlantUML з рушієм smetana).

Ролі ключових класів:

- `ITextElement` - мінімальний контракт рендеру, точка сумісності.
- `TextElement` - центр абстракції: спільний тип, віртуальна точка
  розширення для змісту.
- `Heading` / `Paragraph` / `Link` - конкретні реалізації, кожна знає
  тільки свій формат.
- `TextDocument` - контейнер (композиція): порядок, рендер, зміст
  виключно через поліморфні виклики.
- `DocumentBuilder` - сценарій створення: один API замість розрізнених
  викликів конструкторів і методів документа.

## Збірка і запуск

```bash
dotnet build
dotnet run
```

Вивід текстової частини збігається з оригінальним демо (`Heading`,
`Paragraph`, `Link`, перестановка `MoveElement(4, 3)`, зміст і рендер).
Збірка сувора: увімкнено генерацію XML-документації та
`TreatWarningsAsErrors`, попереджень немає.
